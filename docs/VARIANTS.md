# 从页间扩展电影盲盒、艺术品盲盒

本文是后续开发蓝图，所示通用接口尚未在当前代码中实现。

## 1. 建议的起步方式

先从 GitHub 模板生成独立仓库，各做一款验证。保留相同的沉浸式流程与质量要求，替换具体内容领域；完成第二个品类后，再根据真实重复代码提取共享模块，避免过早设计大而全的平台。

新仓库启动清单：

1. 改项目名称、README、package.json 和页面标题。
2. 移除继承的 `.openai/hosting.json` 中的 **project_id**，新项目注册自己的站点，再保存新的 ID；保留所需逻辑绑定。不要向阅读站点发布新产品。
3. 使用新的服务端配置和数据库；不要复制 `.env.local` 或 `.local-data`。
4. 替换浏览器存储 key、Cookie 名称和测试夹具，避免同域部署时数据串用。
5. 重置内容缓存版本、提示词版本和数据来源枚举；从空数据库进行一次完整测试。
6. GitHub 模板只提供源码；密钥、额度、部署、线上数据都不会自动复制。

## 2. 哪些部分复用，哪些必须改

| 层次 | 可复用 | 品类适配 |
| --- | --- | --- |
| 舞台 | 场景状态、主题牌组、选中归拢、换手动画、响应式、安全区、减少动态效果 | 新主题、牌面内容、颜色与材质 |
| 揭晓 | 等待完成后允许拆开、防止重复动作、连续转场 | 电影票/胶片揭晓海报，画作揭幕/画框；不能只把书封文字替换掉 |
| 预算 | 预留/成功/失败退款、8 小时时段、幂等 UUID | 产品专属 Cookie、缓存空间、并发策略 |
| 外部数据 | 服务端访问、超时、去重、缓存、来源追踪 | 供应商 API、字段解析、内容准入和合法使用范围 |
| 推敲 | 候选 ID 限制、结构化输出、证据引用、受控重试 | 排序维度、提示词、禁用内容和领域事实规则 |
| 详情 | 中文分段排版、来源展示、补全引导 | 电影/艺术专属字段与外部链接 |

## 3. 建议抽象的内容契约

可从 `Book` 逐步提取一个小型核心，而不是不断往 Book 加电影和画作字段：

```ts
type ContentKind = 'book' | 'film' | 'artwork';
type Item = {
  id: string;              // 必须含来源前缀，避免跨库 ID 冲突
  kind: ContentKind;
  title: string;
  creator: string;
  tags: string[];
  facts: Record<string, string | number | string[]>;
  evidence: { id: string; text: string; url: string }[];
  image?: { url: string; credit: string; rights?: string };
  links: { label: string; url: string }[];
};

interface ContentAdapter {
  discover(clues: string[], signal: AbortSignal): Promise<Item[]>;
  enrich(item: Item, signal: AbortSignal): Promise<Item>;
  eligible(item: Item): boolean;
}
```

为每个品类提供自己的 adapter、事实验证器、详情组件和演出配置。优先将 `src/lib/providers`、`server/selection.ts`、`server/details.ts` 与 `src/data/types.ts` 中的阅读假设隔离；随后再改 `App.tsx` 的 Book 依赖。

## 4. 电影版

- 选择线索：心情、想获得什么、时间预算、观影强度、类型、年代。MBTI 可以是探索线索，不应当作人格判断或科学推荐依据。
- 核心事实：片名/原名、导演、年份、时长、国家/语言、类型、无剧透梗概；演员按可验证资料补充。
- 资料准入：排除电视剧单集、预告片、重复条目等非目标内容；同名电影以年份及来源 ID 区分。
- 推荐逻辑：标签决定氛围与观影负担匹配，时间预算是明确约束；不要仅凭片名“看起来治愈”就推荐。
- 详情结构：这是什么电影 → 导演是谁 → 为什么适合这些线索 → 观看提示（无剧透）→ 来源/平台搜索。
- 数据接入前验证：账号与 API 条件、中文覆盖、图片使用规则、地区可用性、请求限制；“在平台搜索”与“已确认可观看”必须区分。

## 5. 艺术品版

- 选择线索：色彩、情绪、想凝视什么、具象/抽象、媒介、时代、观看时间。
- 核心事实：作品名、艺术家、年代或年代范围、媒介、尺寸、收藏机构、来源与图像署名。
- 资料准入：必须有可展示的图像和明确来源；缺图时不应用模型随意生成一张当成真实原作。未知年代、归属有争议等情况按来源保留不确定性。
- 推荐逻辑：从可核对的题材、构图、色彩等证据匹配；不要杜撰艺术家的创作动机。
- 详情结构：眼前是什么 → 艺术家与背景 → 从哪里开始看 → 与所选线索的联系 → 原馆藏页面。
- 展示：揭幕到画框、可放大查看、完整作品和细节明确区分；图像裁切不能冒充完整画面。
- 上线前逐件落实图像许可、署名和再分发条件；有公开网页不等于图片可以任意使用。

## 6. 通用生成模板与验收

生成输入应包含：品类、稳定 ID、核实后的事实、带编号的证据、用户选项、输出结构。输出拆成两个部分：

1. **事实介绍**：仅使用输入证据，引用证据编号；缺资料时省略，不补造。
2. **推荐解读**：明确是阅读/观看建议，用具体事实连接到选项；避免重复标签和空泛赞美。

标签间冲突时说明取舍，不强行声称全部匹配。轻量流程完全不用生成服务，可展示来源简介及固定引导；主动补全才扣推敲机会。

每个品类先建立一组人工检查过的测试样本：常见内容、冷门内容、缺资料、同名条目、相互冲突的选项、不适合的结果、来源中包含恶意指令的文本。验证事实、标签关联、响应时间、成功率和平均调用消耗，再决定是否开放更多候选。

不要把真实 API 调用放进普通 CI；用可复现的夹具验证逻辑，真实供应商测试单独执行并记录。模型路由、预算与失败恢复必须沿用服务端的约束，不能交给前端或提示词保证。

## 7. 推荐实施顺序

1. 一个品类、一家经过核实的数据源、轻量模式先跑通。
2. 实现该品类的内容准入、来源详情与揭晓视觉。
3. 加入推敲排序和解释，使用现有预算/退款流程。
4. 手机操作回归、超时中断回归、小规模试用。
5. 第二个衍生产品稳定后再抽取共享包；各产品保持独立部署、数据和配置。
